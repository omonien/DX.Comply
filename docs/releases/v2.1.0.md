Product page: [DX.Comply on developer-experts.net](https://www.developer-experts.net/en/dxcomply) ([German](https://www.developer-experts.net/de/dxcomply))

## Highlights

- **SPDX 3.0.1 output.** BSI TR-03183-2 version 2.1.0 asks for CycloneDX 1.6 or later, or SPDX 3.0.1 or later. `dxcomply.exe --format=spdx-json --spdx-version=3.0.1` now writes SPDX 3.0.1 JSON-LD with the Core, Software and SimpleLicensing profiles. The `.dxcomply.json` key is `"spdxVersion": "3.0.1"`. SPDX 3.0.1 uses the same packages, IDs, licences and uses graph as SPDX 2.3, and it carries dependency completeness on its relationships, as CycloneDX does with compositions. SPDX 2.3 stays the SPDX default for existing toolchains. The structural check after writing recognises SPDX 3.0.1 (#108).
- **Overview sections in the reports.** The HTML and Markdown reports now open with an origin summary (component counts per origin and per supplier), a licence overview grouped by declared licence with a review hint for copyleft licences that differ from the product licence, and a list of third-party units that no component manifest row matches. The CLI and the IDE log print the count of those units as one line (#112, #113, #114).
- **Warnings for incomplete third-party data, and `--strict`.** Third-party components without supplier or licence are reported as CRA/BSI warnings. `dxcomply.exe --strict` (file key `strict`) writes the SBOM and then exits with code 3 when any CRA/BSI warning was raised, so a CI pipeline can fail on incomplete data (#110, #111).
- **Choose the report content.** `dxcomply.exe --report-content=overview|units|all` selects what the HTML and Markdown reports contain: the overview sections, the list of all units with their SHA-256 hashes, or both. `all` is the default and keeps the previous reports. The `.dxcomply.json` key is `report.content`, and the IDE has a Report content setting. The SBOM always stays complete. This came from user feedback (#126).
- **ARM and LLVM linker maps.** Android, iOS, Linux and macOS ARM builds link with LLD. Its map file is now read: object files become units, archive members become native components. Build outputs follow the platform naming (for example `lib<Project>.so` on Android), and the map hints name the right IDE setting for each platform (#99, #100, #101, #105).

## Changes

- **CLI name.** The command-line tool is `dxcomply.exe` everywhere: project file, help text, hints and documentation. Help and hints show the name of the executable that is actually running (#102, #106, #107).
- **CLI version.** `dxcomply.exe` reads its version number from its own version resource instead of a constant in the code (#41).
- **Supplier from the .dproj.** When no supplier is set, the CompanyName from the version info of the `.dproj` is used as the fallback (#88).
- **Version fallback.** A file without a version of its own gets its last modification time in UTC as an RFC 3339 timestamp, marked with the `versionSource` property, as section 5.2.2 of the TR describes. A third-party `.dcp` no longer takes the product version (#109).
- **Validator.** The structural check requires CycloneDX 1.6. SPDX output names the licence list version it was written against (#115).
- **DLL lookup.** DLLs and BPLs named by the project are also found in an `Installer` folder in the project tree, with a hash, instead of being recorded from a system directory without one (#98).
- **Group by source folder.** `dxcomply.exe --report-group-by-folder` (file key `report.groupByFolder`) groups the third-party units without manifest by unit prefix and source folder, so libraries that share a prefix but live in different folders show as separate groups. The default stays grouping by prefix. This came from user feedback (#132).
- **Licence of the built program.** The built program (the `.exe`, `.dll` or `.bpl` of the project) now carries the product licence in CycloneDX JSON and XML, as it already did in SPDX. The licence overview of the reports lists it under the product licence instead of under "No licence information" (#131).
- **Libraries below the Delphi folder.** Only the folders Embarcadero ships (`source`, `lib`, `include`, `bin`, `bin64`, `imports`, `ObjRepos`, `Redist`) count as Embarcadero RTL, VCL or FMX. A library installed into another folder below the Delphi root, such as `Extras`, is now third party (#134).
- **Shared libraries outside the project.** A project search path inside the Delphi folder no longer makes its units "Local project". A DCU in the project's DCU output folder takes the origin of its `.pas` when that source is found in the search path, so a third-party unit compiled into the project stays "Third party" (#133).
- **Longest manifest prefix wins.** When several `units_prefix` entries match a unit, the longest one wins, whatever the order of the rows. `Neslib.Xml` now gets its units even when a row with `Neslib` comes first. `units_exact` and `own_code_units` keep their priority (#129).
- **`units_exclude` in the component manifest.** A row can list units that its prefixes do not match, so a short prefix such as `Ab` can be used without taking units of other libraries. The warning for a prefix shorter than 3 characters now says that the prefix is still applied. This came from user feedback (#140).
- **Shared output directory.** `outputDir` in `.dxcomply.json`, and **SBOM and report directory** in the IDE options, send `bom.json` and the HTML and Markdown reports to one folder. The folder is created if needed. `--output=<file>` still names the SBOM file and wins over `outputDir`. `--include-platform-in-output` still decorates the file name inside that folder. `report.output` remains an optional report-only override (#146).
- **SBOM header data in the reports.** The HTML and Markdown reports show the SBOM creator, supplier, supplier URL, licence and product version (#104).
- **Generation time.** The README and the BSI field table now state that an archived SBOM records when it was generated inside the file (CycloneDX `metadata.timestamp`, SPDX `creationInfo.created`, SPDX 3.0.1 `created` on CreationInfo, and the report row Generated At), and that `--output` is how to choose the archive file name (#147).
- **Documentation.** The README and docs/BSI-TR-03183-2.md now state that the CRA asks for a commonly used, machine-readable format, and that the format versions come from the TR. The retention period follows CRA Article 13(13): 10 years after the product is placed on the market, or the support period if that is longer. A new FAQ entry explains which SBOM format to pick (#116). A docs pass for 2.1 adds the ARM map setting, the version fallback and the report content option to the README, and completes the unit table in docs/Architecture.md. The CI guide uses `retention-days: 3653`, which is 10 years including leap days, and says that GitHub caps artifact retention at the repository limit, so the SBOM also belongs on the release or in an archive (#130). The README explains how to add supplier and licence for libraries that ship no metadata, with a matching FAQ entry (#135).
