## Highlights

- **Corroborated manifest prefixes.** A `units_prefix` assigns a library only when the prefix contains a dot, such as `FMX.TMSFNC` or `Neslib.Xml`, and the unit file is not in an Embarcadero product path. A prefix with no dot, such as `Adv`, `TMS`, `DEC`, `GDIP` or `HTML`, does not assign. The unit keeps the origin from its path. `units_exact` still wins, then `own_code_units`, then the longest `units_folder` or `own_code_folders`. A folder on a product path still matches. Prefer `units_folder` or `units_exact` over a short prefix. The HTML and Markdown reports list a refused prefix under **Prefix matches not applied** (unit, prefix, row, kept origin). The log line names the same four fields. `match.prefixes` set to `legacy` in the components file, `matchPrefixes` in `.dxcomply.json`, or `--match-prefixes=legacy` still applies a prefix with no dot outside a product path, for this release. It never reassigns a product shipped path (`source\rtl`, `source\vcl`, `source\fmx`, the other product source trees, or `lib\<platform>\release` and `debug`). A vendor is listed for every matched manifest row, including when those units are classified as local project code.

- **Uses-clause dependency graph.** Where a unit's Pascal source was read, CycloneDX `dependencies` now records a direct edge to each unit named in its interface or implementation uses clause, when that unit is already in the same SBOM. The built program still depends on runtime packages, then external DLLs, then the units that no other unit uses. A uses B and B uses C writes those two edges, and the program depends on A, so the chart has more than one level. A cycle is kept in both directions. A cycle that no unit outside it uses keeps its lowest component index on the program. `System` and `SysInit` stay on the program. They are not edges from every unit. A unit with no readable source stays a leaf and is marked `net.developer-experts.dx-comply:dependencies` = `unresolved-no-source`. Each `.pas` is parsed once: the MAP resolver and the uses-clause walk share that list with the SBOM write. SPDX 2.3 writes the same edges as `DEPENDS_ON`. SPDX 3.0.1 writes them as `dependsOn`, with the same completeness as CycloneDX compositions. The program still `CONTAINS` every linked unit. `dxcomply.exe --library` writes the same edges for a shipped `.pas`, `.dpr`, or `.dpk`. The library depends on the Pascal files that no other file uses, and on every other file. Library compositions still describe the file set. Reports do not list these edges. CycloneDX output stays 1.6 (#43).
- **Manifest path variables.** `$(name)` in `units_folder` and `own_code_folders` is replaced before the path is normalized. A relative result is still resolved from the components file directory. Pass `--define:name=value`, `--define=name=value`, or `--define name=value` (repeatable; the last value of a name wins; spaces and backslashes are kept). The same names are the `defines` object in `.dxcomply.json` and **Manifest path variables** in the IDE options. With `--ci`, a command-line name wins over the same name in the file, and other file names stay. In the IDE, the options are the base and the project file wins for that name. `$(env.NAME)` reads environment variable `NAME` only when `env.NAME` is not defined. A definition wins. `$(NAME)` does not read the environment. `$$(name)` is the characters `$(name)`. An unknown name fails the run (exit code 1) and names the variable, the row, and the field. A bad `--define` is exit code 2. The log line starts with `Info:` and names each variable that was used. The SBOM and the reports contain the expanded path. `dxcomply.exe --library` expands the same fields (#185).

- **Shared output folders.** A clean setup gives every project its own output folder and assembles the install folder in the installer, so one SBOM does not pick up another tool. When an existing setup still builds several projects into one folder, the flat scan lists every executable and DLL there. DX.Comply writes one info line when that folder contains more than one executable, and names them. The SBOM is unchanged. Limit the list with `--include=MyTool.exe`. An include list replaces the default extensions. Add a needed DLL with another `--include`. Do not use `--exclude=*.exe`. The same list is `include` in `.dxcomply.json`, read with `--ci`. See the Output folders section in the README and in docs/CI-Integration.md (#189).

- **CPE on a component manifest row.** An optional `cpe` string is written on the library component that row describes. CycloneDX 1.6 JSON and XML use `cpe`, after `copyright` and before `purl`. SPDX 2.3 adds an `externalRefs` entry with `referenceCategory` `SECURITY` and `referenceType` `cpe23Type` for a CPE 2.3 formatted string (`cpe:2.3:part:vendor:product:version:...`), or `cpe22Type` for a CPE 2.2 URI (`cpe:/part:vendor:product:version:...`). SPDX 3.0.1 adds an `externalIdentifier` of type `cpe23` or `cpe22`. CycloneDX 1.6 accepts both forms, so both are kept. Anything else is a warning and the value is left out. The SBOM is still written. DX.Comply does not derive a CPE from the component name or version. A row without `cpe`, or with only spaces, is unchanged. `dxcomply.exe --library` reads the same manifest: a shipped `.pas`, `.dpr`, or `.dpk` that matches a row carries that row's `cpe` (#181).

## Fixes

- **Numeric file version.** The version of a binary in the SBOM and in the HTML and Markdown reports is the numeric file version (a.b.c.d from the fixed file info). The FileVersion string, then the ProductVersion string, is used only when that fixed file info is absent. A string such as "6, 10, 5, 0" no longer replaces 6.10.5.0 (#188).

## Test coverage

836 DUnitX tests (809 on main after the CPE field, the prefix rule, and the library-mode product-path test, plus 27 path-variable tests). The path-variable tests cover `--define:name=value`, `--define=name=value`, and `--define name=value`, a quoted value with spaces and backslashes, the last value of a name, a rejected name, expansion before folder matching, a relative result from the components file directory, text appended after a placeholder, `$(env.NAME)` when that name is not defined, a definition of `env.NAME` winning over the environment, a plain `$(NAME)` that does not read the environment, an undefined name that names the variable, the row, and the field, `$$(name)` left as the characters `$(name)`, the rewritten manifest JSON, `defines` in `.dxcomply.json` with a command-line name winning and other names kept, IDE then file then CLI, library mode with no placeholder left in the SBOM or the HTML report, and a library-mode run that fails when a name is undefined. The prefix tests cover a product-path DCU that a short prefix does not reassign, a dotted prefix that still assigns, `match.prefixes` legacy outside a product path, the supplier list for local-project units, the Prefix matches not applied section in HTML and Markdown, and `--match-prefixes`. The library-mode test places a shipped `.pas` under `source\rtl` and checks that a short prefix does not assign it when the project scan has an install root. The CPE tests cover a valid CPE 2.3 formatted string, a valid CPE 2.2 URI, an invalid value and a non-string (warning, value omitted, parse still succeeds), a missing or blank value, and the written field in CycloneDX JSON, CycloneDX XML, SPDX 2.3, and SPDX 3.0.1. Those documents still pass the structural check. The same three formats are covered for `dxcomply.exe --library` when a shipped `.pas` matches a row. The uses-clause tests cover interface and implementation uses, `System` and `SysInit` on the program, one parse per source file on the MAP path and on the uses-clause path, the SPDX 3.0.1 `dependsOn` edges, library-mode uses edges, and the same chain through `Generate` for a MAP build and for `--library`. The chain, cycle, and DCU-leaf tests expect the program to list only the units that no other unit uses. Six file version selection tests pass fixed file info and version strings, with no binary. They cover a numeric version that differs from the FileVersion and ProductVersion strings, a numeric version with empty strings, 0.0.0.0 kept when fixed file info is present, the FileVersion string when fixed file info is absent, a blank FileVersion falling through to ProductVersion, and an empty result when both strings are blank. A shared output folder with more than one executable logs one info line that names those executables and points at the Output folders section. One executable in that folder does not, including when `scanDirs` adds another executable. The SBOM still lists every scanned executable.
