## Highlights

- **Uses-clause dependency graph.** Where a unit's Pascal source was read, CycloneDX `dependencies` now records a direct edge to each unit named in its interface or implementation uses clause, when that unit is already in the same SBOM. The built program still depends on runtime packages, then external DLLs, then the units that no other unit uses. A uses B and B uses C writes those two edges, and the program depends on A, so the chart has more than one level. A cycle is kept in both directions. A cycle that no unit outside it uses keeps its lowest component index on the program. `System` and `SysInit` stay on the program. They are not edges from every unit. A unit with no readable source stays a leaf and is marked `net.developer-experts.dx-comply:dependencies` = `unresolved-no-source`. Each `.pas` is parsed once: the MAP resolver and the uses-clause walk share that list with the SBOM write. SPDX 2.3 writes the same edges as `DEPENDS_ON`. SPDX 3.0.1 writes them as `dependsOn`, with the same completeness as CycloneDX compositions. The program still `CONTAINS` every linked unit. Reports do not list these edges. CycloneDX output stays 1.6 (#43).

## Test coverage

787 DUnitX tests (782 in v2.1.0, five added). The new tests cover interface and implementation uses, `System` and `SysInit` on the program, one parse per source file on the MAP path and on the uses-clause path, and the SPDX 3.0.1 `dependsOn` edges. The chain, cycle, and DCU-leaf tests now expect the program to list only the units that no other unit uses.
