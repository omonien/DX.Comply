## Highlights

- **Grouped dependency graph.** `dependencies` is no longer one list of every component under the project name. The project depends on the built exe, dll, or bpl. That binary depends on runtime packages, then external DLLs, then linked units. If there is no deliverable, the project still depends on every component directly (#42, #51).
- **DLL imports.** A DLL name in a `const`, passed to `LoadLibrary`, `LoadLibraryA`, `LoadLibraryW`, `LoadLibraryEx`, `SafeLoadLibrary`, `GetModuleHandle`, or `LoadPackage`, is recorded. So is `external SomeIdentifier` when the name comes from an include file, including a name chosen under `{$IFDEF}` (#24, #45, #51). The component is an `external-reference`. The hash stays empty when the file was not opened.
- **SPDX 2.3 fixes.** Package IDs use the relative path plus a short SHA-1 of that path, so two files with the same name no longer share one ID. `creationInfo.created` is UTC with a `Z` suffix. External references are percent-encoded `pkg:generic` locators. Scanned packages set `licenseConcluded` and `licenseDeclared` to `NOASSERTION`. A manifest library uses the licence from its row. A supplier you set is written as `Organization: <name>` (#39, #40, #50, #52).
- **Config file precedence.** `.dxcomply.json` accepts `configName` (and the existing `configuration` key) and `platform`. The file is still loaded only with `--ci`. Built-in defaults are applied first, then keys in the file, then options you actually pass. An option you leave off the command line does not replace the file with the default (#50, #52).
- **Narrower binary scan.** By default the SBOM lists the exe, dll, or bpl the project names, plus other binaries in that same directory. Subfolders are not walked, so `setup`, `tools`, and old build directories stay out (#38, #55). `--scan-dir=<path>` (repeatable, or `scanDirs` in the config file) adds a directory. `--scan-tree` restores the old recursive walk of the output directory. It is deprecated and kept for this release.
- **Wording.** Public text describes DX.Comply as build evidence and a component list. That list is a starting point for the SBOM part of EU CRA technical documentation. It does not make a product compliant, and it does not produce the rest of the technical file (#54).
- **Delphi 7 from the CLI.** `--project` accepts a Delphi 7 `.dpr` with its `.dof` and `.cfg`, or a `.dpk` when a package has no `.dproj`. Delphi 2005 and 2006 can pass a `.bdsproj`. Pass `--delphi7-root` or set `delphi7Root` when the Delphi 7 tree is not in the registry (#57).
- **Component manifest.** `--manifest=<file>` (or `manifest` in `.dxcomply.json`) reads a DelphiSBOM schema 1.0 components file, the format published by @ijbranch. Matched units stay as evidence. The SBOM adds one library component for the row, with supplier, licence, version, type, and package URL (#20, #56). A sample is in `docs/samples/components.sample.json`.
- **BSI TR-03183-2 fields, CycloneDX 1.6.** CycloneDX JSON and XML are written as 1.6. SPDX stays at 2.3. SPDX 3.0.1 is out of scope. The writers fill the fields they can take from the build or from values you set, including SHA-512, a distribution external reference on a deployable file, the file name and the executable, archive, and structured properties, and `--sbom-creator` for one email address or one http(s) URL. This is not a certification and it is not full coverage of the technical guideline. The field list is in `docs/BSI-TR-03183-2.md` (#60).
- **Direct uses edges.** Where a unit's Pascal source was read, the document records a direct edge to each uses name that is already a unit in the same SBOM. A uses B and B uses C writes those two edges, not an edge from A to C. A cycle is kept as both directions. A unit with no readable source stays a leaf and is marked `unresolved-no-source`. CycloneDX compositions say which sets are complete. SPDX writes `DEPENDS_ON` for the same edges. Part of #43 (#61).
- **Companion reports from the CLI.** `--report=html`, `--report=markdown`, `--report=both`, or bare `--report` writes the HTML and Markdown reports next to the SBOM. They stay off unless you ask (#30).
- **Separate files per target.** `--include-platform-in-output` appends `.<Platform>.<Config>` to the default file name, for example `bom.Win64.Release.json`. It is ignored when `--output` is set (#25).

The reference sample is ConwaysLifeFMX from https://github.com/Embarcadero/RADStudio13Demos.git, project `Object Pascal/RTL/Parallel Library/FMX/ConwaysLifeFMX.dproj`, built Release/Win32 with a map file. The example SBOM is regenerated from that demo and will replace `docs/examples/AlienInvasion.bom.json` as `docs/examples/ConwaysLifeFMX.cdx.json`. That new file is not in this tree yet. The file still checked in is the earlier AlienInvasion CycloneDX 1.5 document. New CycloneDX output is 1.6.

## Breaking changes

- CycloneDX JSON and XML now use `specVersion` 1.6. A consumer that accepts only 1.4 or 1.5 will reject the new files. SPDX output stays 2.3 (#60).
- The default scan no longer walks subdirectories of the output folder. SBOMs are smaller. Binaries that used to appear from `setup`, `tools`, or an old build folder are omitted unless you pass `--scan-dir` (#38, #55).
- The CycloneDX dependency list changed shape. The project name depends on the built program. That program depends on runtime packages, external DLLs, and linked units, in that order. It is no longer a single edge list from the project to every component (#42, #51).
- SPDX package IDs changed. An ID is no longer the file name alone. `creationInfo.created` is UTC (`YYYY-MM-DDThh:mm:ssZ`). External reference locators are percent-encoded (#39, #52).
- With `--ci`, a `.dxcomply.json` value is kept when you do not pass the matching flag. The built-in default (`Release`, `Win32`, `cyclonedx-json`, `bom.json`) no longer replaces the file (#50, #52).
- `--product` and `--version` now change the name and version written into the SBOM. Previously the project values were used even when the flags were set (#26).
- CycloneDX XML metadata and component children follow the 1.6 element order (#60).

## Bug fixes

- An empty output directory no longer raises `EInOutArgumentException` (#47, #48).
- `$(VarName)` in a `.dproj` path is expanded from the process environment. Unknown tokens are left as written (#27).
- The Project menu item is added when the IDE menu exists, including when the package is loaded from GetIt before that menu is ready (#21).
- The Project menu entry is found by the component name `ProjectMenu`, not by the localized caption, and retried for about 30 seconds and on a later IDE notification after a GetIt install. Reported by Markus Humm (#63).
- The options page keeps each edit clear of the Browse button and scales with the IDE DPI and the page width (#63).
- README.md and the icons are embedded in the IDE package, so the info page does not need a repository checkout (#63).
- The About dialog reads the version from the BPL version resource. A missing resource is shown as unavailable instead of a fixed 1.0.0.0 (#63).
- The docs say `dxcomply.exe` comes from the release ZIP, the installer, or a build of `src/CLI/DX.Comply.CLI.dproj`. GetIt installs the IDE plugin only (#63).
- Searching for the build script does not crash when the project directory is a drive root (#19).
- Units resolved from the project search path are classified as local project, not third party (#22).
- DLL references inside units found as composition evidence are scanned as well (#23).
- A MAP file that contains no unit list produces a warning (#15). Named `Platform` entries are used to detect LLVM and mobile targets (#16). The expected MAP path no longer depends on a missing `DCC_ExeOutput` (#15).
- Windows API errors from the build orchestrator are reported in English (#18).
- When the optional rebuild fails and generation continues, the message is a progress line, not `[ERROR]`. The IDE dialog points at the Messages window rather than a log file that does not exist (#29, #31).
- The tool version stored in the SBOM is the version resource of the module that contains `DX.Comply.VersionInfo` (#53).
- Include and exclude patterns are matched against the path relative to the directory being scanned. `/` and `\` are treated the same. A pattern that cannot be compiled is reported (#53).
- The Deep-Evidence build runs `DelphiBuildDPROJ.ps1` from the copy installed next to DX.Comply. Arguments are quoted. The process is stopped after 30 minutes (#53).
