# BSI TR-03183-2 fields

DX.Comply reads [BSI TR-03183-2](https://www.bsi.bund.de/SharedDocs/Downloads/EN/BSI/Publications/TechGuidelines/TR03183/BSI-TR-03183-2_v2_1_0.pdf?__blob=publicationFile&v=6), version 2.1.0, 20 August 2025. Section 4 of that edition requires CycloneDX 1.6 or later, or SPDX 3.0.1 or later. CycloneDX JSON and XML are written as 1.6. SPDX stays at 2.3. SPDX 3.0.1 is out of scope, so the SPDX file does not meet that minimum. The tables below say which required and additional fields that output carries, and which it does not.

This is not a certification. It is not a claim that a generated file meets TR-03183-2.

## What the technical guideline requires

SBOM level (Table 2):

| Field | What DX.Comply writes |
|---|---|
| Creator of the SBOM (email, or a URL when there is no email) | CycloneDX 1.6 `metadata.manufacturer`, one organizational entity. An email is `contact.email`. A URL is `manufacturer.url`. The deprecated `manufacture` element is not written. The TR example shows `manufacturer` as an array, which `bom-1.6.schema.json` does not accept, so the writer uses one object. SPDX 2.3 has no URL on a creator, so an email is `Person: <email> (<email>)` and a URL is `creationInfo.comment`. Written only when you set `--sbom-creator` or `sbomCreator`. |
| Timestamp | `metadata.timestamp` and SPDX `creationInfo.created`. UTC is used when the clock value is UTC. |

Each file component (Table 3):

| Field | What DX.Comply writes |
|---|---|
| Component creator (email or URL) | Not known for a scanned file. Omitted. A manifest library uses `vendor` as `supplier`. An email vendor is also `supplier.contact.email` (CycloneDX) and SPDX `originator` `Person: <email> (<email>)`. `vendor_url` is the URL. That is not `manufacturer`. |
| Component name | File name for a scanned file. Product name for the primary component. Manifest `name` for a library. |
| Component version | Product version, or the manifest `version`. A scanned file keeps the first 12 hex characters of its SHA-256. The file modification time is not used. |
| Filename | `bsi:component:filename`, and SPDX `packageFileName`. The name only, not the path. Omitted when there is no file name. |
| Dependencies, with completeness | The program depends on runtime packages, then external DLLs, then linked units. A unit whose Pascal source was read also depends on the units named in its uses clauses, when those units are already in this SBOM. CycloneDX `compositions` mark each set `complete` or `incomplete`. The rule is under Dependency completeness. SPDX 2.3 has no completeness field. |
| Distribution licence | SPDX identifier, SPDX expression, or a name when a manifest row has one. `Commercial` and `Proprietary` stay `license.name`. Acknowledgement is `concluded` for the distribution licence we assert. A scanned file stays `NOASSERTION` in SPDX and has no CycloneDX licence. |
| SHA-512 of the deployable component | Component `hashes` with `alg` `SHA-512`, next to SHA-256, when the file could be opened. An executable or an archive that was hashed also gets `externalReferences` type `distribution` with that same SHA-512. Unit evidence and a DCP do not. SPDX checksum algorithm `SHA512` stays on the package. |
| Executable property | `bsi:component:executable` = `executable` or `non-executable`. |
| Archive property | `bsi:component:archive` = `archive` or `no archive`. |
| Structured property | `bsi:component:structured` = `structured` or `unstructured`. |

Additional fields (Tables 4 and 5), written only when the value exists:

| Field | What DX.Comply writes |
|---|---|
| SBOM-URI | Not known. The CycloneDX `serialNumber` is a generated URN, not a URL you supplied. |
| Source code URI | Omitted. |
| URI of the deployable form | No download URL is known. `bom-1.6.xsd` requires `url` on an external reference, so the distribution reference uses the same `file:` locator already written as `purl`. That locator is not a download URL. The TR example omits `url`. |
| Other unique identifiers (CPE, purl) | Package URL when the writer already has one (`file:` for a scanned file, manifest `purl` or `pkg:delphi` for a library). CPE is omitted. |
| Original licences | A manifest row is a source declaration. An SPDX id or a named licence is written a second time with acknowledgement `declared`. An SPDX expression is not copied that way: CycloneDX 1.6 `licenseChoice` allows only one expression, and that one is `concluded`. |

Optional Table 6 fields (effective licence, source-code hash, security.txt URL) are omitted. The source-code hash algorithm is not defined by the guideline yet.

## Licence acknowledgement

CycloneDX 1.6 puts `acknowledgement` on a `license` object, and as a sibling of `expression`. The allowed values are `declared` and `concluded`.

- The distribution licence we assert is `concluded`.
- Where the manifest declares an SPDX id or a name, the same value is also written as `declared`.
- An expression stays a single `concluded` entry, because the schema allows only one expression in `licenses`.
- SPDX 2.3 has no acknowledgement. A manifest package still sets `licenseDeclared` and `licenseConcluded` to the same token. A scanned file stays `NOASSERTION` for both.

## Deployable hash

`bom-1.6.xsd` order for a component that has these children is: hashes, then licences, then purl, then externalReferences, then properties. The distribution reference is:

```xml
<externalReferences>
  <reference type="distribution">
    <url>file:App.exe</url>
    <hashes>
      <hash alg="SHA-512">...</hash>
    </hashes>
  </reference>
</externalReferences>
```

`type` is an attribute. `url` comes before `hashes`. A website reference from a manifest uses the same shape, `type="website"`, and only a `url`.

Unit evidence and a DCP keep SHA-256 and SHA-512 in `hashes` and do not get a distribution reference. An executable or an archive does. A logical component (the primary component, a manifest library) gets neither a file hash nor a distribution reference. A missing file gets the file name and the three properties, and no hash.

## How file properties are chosen

The executable, archive, and structured values come from the artefact type and the file extension. The file is not opened to decide them.

- Executable: artefact type application, library, package, or runtime-package, or a name ending in `.exe`, `.dll`, or `.bpl`. A source-scanned DLL is executable. A Pascal unit, a DCU, a DCP, a resource, and a MAP file are non-executable.
- Archive and structured: `.zip`, `.7z`, `.tar`, `.tgz`, `.tar.gz`, `.tar.bz2`, `.rar`, `.jar`, `.nupkg`, `.iso`, `.cab`. Everything else is `no archive` and `unstructured`. A linked binary is unstructured, which matches section 8.1.6. A self-extracting archive is not detected.

Logical components do not get a file name, a hash, or these three properties. The primary component and a manifest library are logical components. A runtime package or a missing DLL still gets the file name and the three properties, and it does not get a hash.

## Creator contact

`--sbom-creator` and `sbomCreator` accept one email address or one `http://` or `https://` URL. An empty value is ignored in the config file. On the command line an empty flag is an error. Any other text is an error: the CLI rejects it while parsing, and a bad value in `.dxcomply.json` stops generation. The supplier name and a Delphi 7 `CompanyName` are not reused as this contact.

## Dependency completeness

CycloneDX `compositions.aggregate` is `complete` or `incomplete`.

A unit is `complete` when its `.pas` was read and every name in its interface and implementation uses clauses matches a unit already in this SBOM. An empty uses clause is complete. The match is the unit file name, or the name after the last dot when that short name belongs to exactly one unit. A name that matches two units is not used. No component is added for a name that is not already in the SBOM, and that unit stays `incomplete`.

A manifest library is `complete`. Its `dependsOn` list is the units the manifest row matched. That row is the declaration we have.

The primary component stays `incomplete`. The built program stays `incomplete`. The MAP list, the runtime package names, and the DLL names are what the build showed. A runtime package is not opened, and a third-party `.dpk` is not parsed, so its contents are not edges. An external DLL stays `incomplete`. The scanner records the DLL name, not which unit imported it, so the DLL stays on the program. Other files that are not units stay `incomplete`.

A unit with no readable `.pas` stays `incomplete` and gets `net.developer-experts.dx-comply:dependencies` = `unresolved-no-source`. A DCU is that case. The property is not written when the source was read.

The incomplete aggregate is written first. It starts with the project name, then every component that is not complete, in component order. The complete aggregate is written only when at least one component is complete. An empty set is omitted. A document with no project name omits `compositions`.

Edges are direct. A uses B and B uses C writes those two edges, not an edge from A to C. A uses B and B uses A writes both edges. The builder does not walk them again, so a cycle does not loop. Targets are sorted by unit name, case-insensitive, then by component index. The grouped list on the program is not re-sorted.

A component with no outgoing edge is left out of `dependencies`. An empty `dependsOn` array is not written. TR-03183-2 describes components without dependencies as empty elements. This writer omits them, so a document with no deliverable keeps a single dependency entry for the project.

SPDX 2.3 has no completeness field. A uses edge is `DEPENDS_ON` between the two unit packages. The program still `CONTAINS` each linked unit. A manifest library still `DEPENDS_ON` its units.

On a Win32 or Win64 build the uses clause is read once while the unit is resolved, and the SBOM write reuses that list. The fallback that discovers units from source when there is no MAP file can read a `.pas` a second time. Compiler units such as System and SysInit are not given edges beyond the MAP link from the program.

## What is still open

- SPDX output is 2.3. SPDX 3.0.1 is out of scope. The SPDX file does not meet the SPDX minimum in TR-03183-2 version 2.1.0.
- A scanned file version is still the 12-hex SHA-256 prefix, not the file modification time in RFC 3339.
- Dependency completeness follows the rule above. It is not a full closure of third-party DCU libraries or of runtime package internals. SPDX 2.3 has no completeness field.
- The SBOM creator is written only when you pass an email or an http(s) URL. A company name is rejected.
- executable, archive, and structured are inferred from the artefact type and the extension, not from file contents. A self-extracting archive is not detected.
- The XML tool list still uses the legacy `tool` element (`vendor`, `name`, `version`). `bom-1.6.xsd` accepts that element and marks it deprecated. JSON uses `tools.components`.
- The repository does not vendor `bom-1.6.xsd`. The structural checker encodes the 1.6 child order of `metadata` and `component`. That check is not xmllint.
